# Design

## Context
现有应用为 Flask、静态 HTML 及官方 Python SDK，已有订单验证和状态规范；Combo 使用单独 RFQ 流程。新系统要求独立运行且沿用真实数据来源。

## Goals / Non-Goals
**Goals:** 以 PostgreSQL 持久化任务截止时间和业务状态；通过受控适配器调用外部数据和交易接口；让每个阶段可独立验证。
**Non-Goals:** 不迁移或破坏现有 Dashboard，不伪造第三方赛事、报价、成交或钱包状态，不自动部署和执行真实交易测试。

## Decisions
以独立目录和进程实现 FastAPI、Vue 与工作进程，所有调度时间保存 UTC，界面转换为 UTC+8。赛事和 Polymarket 市场通过来源 ID、球队及时间校验匹配，模糊匹配须人工确认。CLOB 和 Combo RFQ 分别建模，提交意图与关注在对外请求之前事务落库；超时进入未知状态并对账，禁止盲目重发。外部凭证从部署环境或受限密钥文件加载，不写入仓库和日志。

## Risks / Trade-offs
[第三方套餐、覆盖范围或 Combo 权限不足] → 明示不可用并保留可恢复状态，不用虚构数据。 [队名翻译缺失] → 显示原名及待补全标记，允许管理员维护别名。 [进程重启和重复执行] → 持久截止时间、数据库锁与唯一键，先校验到期再处理。
