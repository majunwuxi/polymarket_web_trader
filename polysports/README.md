# PolySports

本目录是独立的 PolySports 项目，提供管理员认证、足球和 NBA 赛程同步、赛事中心、球队译名维护、关注、独立后台调度、Polymarket 市场映射、只读钱包状态、单场限价订单及 Combo RFQ 组合交易。界面不显示虚构业务数据。不需要启动仓库原有 Flask Dashboard。测试记录和真实环境验证边界见 [ACCEPTANCE.md](../ACCEPTANCE.md)。

## 环境与配置

需要 Python 3.11–3.14、uv、PostgreSQL 15+、Node.js 22.12+（22.x）、24.x 或 26+ 和 npm（测试工具链要求）。在本目录运行 `uv sync --locked --group dev`，在 `frontend/` 运行 `npm ci`。

复制 `.env.example` 为 `.env`，设置 `POLYSPORTS_DATABASE_URL`（`postgresql+psycopg://用户名:密码@主机:端口/数据库名`）、`POLYSPORTS_PUBLIC_ORIGIN`（浏览器访问的 HTTPS 源，如 `https://sports.example.com`，不带末尾斜线或路径）和 `POLYSPORTS_AUTH_SECRET`。密钥必须是至少 32 字节的随机值，可以用 `python -c "import secrets; print(secrets.token_urlsafe(48))"` 生成；替换示例占位符并妥善保存。`.env` 已被 Git 忽略，不要提交真实凭据。更换密钥会使现有会话失效。环境变量优先于 `.env`；以下后端命令应在本目录运行。

## 迁移、初始化及运行

```bash
uv run --locked alembic upgrade head
uv run --locked python -m backend.init_admin --username 管理员用户名
uv run --locked uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

初始化命令交互式要求输入两次至少 12 个字符的密码，不通过命令行参数传递密码。系统只允许一个管理员。健康探针为 `http://127.0.0.1:8000/api/v1/health/live`，仅表示进程存活，不代表数据库就绪。

前端在 `frontend/` 执行 `npm run dev`，开发代理将 `/api` 转至本地 8000 端口；生产构建执行 `npm run build`。登录 Cookie 设置了 Secure，访问登录页面须通过可信 HTTPS 反向代理，并且浏览器实际源须与 `POLYSPORTS_PUBLIC_ORIGIN` 完全一致。反向代理应只向应用传递经过可信代理验证的客户端地址，不能信任任意客户端自带的转发头，否则按 IP 限流会失准。正式 Nginx、systemd、凭据和备份恢复步骤见 [DEPLOY.md](../DEPLOY.md)。

## 赛事数据同步

足球和 NBA 赛程均来自 Polymarket 公开市场发现（Gamma），按运动、赛事范围和未来 36 小时窗口筛选。交易所确认接受订单后，赛果绑定与比分核验分别使用 API-Football（足球）和 BallDontLie（NBA），需配置 `POLYSPORTS_API_FOOTBALL_KEY` 与 `POLYSPORTS_BALLDONTLIE_KEY`；市场结算状态另由 Polymarket data-api `/v2/resolutions` 只读查询。密钥只从本机环境加载，不写入数据库或 Git。迁移完成后，可手动同步：

```bash
uv run --locked python -m backend.sync_cli football
uv run --locked python -m backend.sync_cli nba
```

每次调用以实际开始时间为起点，获取并精确过滤未来 36 小时；足球只展示 Polymarket 已开设、可识别为胜平负的比赛，市场关闭后保留历史但不再显示在未来列表。分页失败或来源限流记为失败，不删除既有赛事。Polymarket 来源赛事必须先完成赛果来源绑定才能关注或下单；绑定候选与赛果查询代码已实现，但需要有效密钥在目标环境联调确认。自动同步需要独立 worker，默认按 UTC 00:00、08:00 同步，可在页面修改。中文名称需管理员核实维护，未知队徽以占位显示。

足球与 NBA 的中文名和队徽可使用用户提供的 `sportsmatch` 球队资料快照作为展示参考；只有同运动的完整英文名称唯一匹配时才使用。人工确认的中文名与已有非占位队徽优先，目录不会修改数据库或作为交易身份核验依据。快照版本见 `backend/team_data/README.md`。

足球赛事仅包含指定范围：英超、德甲、意甲、西甲、法甲、荷甲、葡超、瑞超、挪超、芬超、巴甲、阿甲、美职联（MLS）、欧冠、欧罗巴、欧协联、亚冠精英、世界杯、各洲世预赛、欧洲杯、欧国联和亚洲杯；不含英冠、德乙、法乙、荷乙等乙级联赛。仅在 Polymarket 足球赛事标签能唯一确认时收录；截至本次核验，公开体育目录中没有可确认的亚洲杯标识，因此亚洲杯尚不能自动识别。未知或冲突标签不猜测，既有历史不删除。

点击赛事“查看详情”会打开弹窗并只读查询 Polymarket 市场、选项与来源参考价格，显示查询时间。Polymarket 来源足球比赛按来源比赛 ID 核对；其他来源按运动、主客队和时间寻找候选，候选不会自动变成交易映射。数据不可用时显示错误，不把空白或旧数据当作真实报价；参考价格不保证可以成交。

接口依据：赛程与市场来自 [Polymarket Gamma 事件游标分页](https://docs.polymarket.com/api-reference/events/list-events-keyset-pagination) 和 [市场字段](https://docs.polymarket.com/api-reference/markets/list-markets)；结算来自 Polymarket data-api；赛果绑定来源见 [API-Football fixtures](https://www.api-football.com/documentation-v3) 与 [BALLDONTLIE NBA games](https://docs.balldontlie.io/#get-all-games)。

## 后台任务和关注

完成数据库迁移后，在本目录的独立终端运行：

```bash
uv run --locked python -m backend.worker
```

worker 通过 PostgreSQL 生成和领取持久任务，允许多个实例并发运行；进程退出或机器重启后重新启动 worker 即可恢复到期任务。任务只会在数据库时间达到截止时间后被领取，过期租约的旧结果不会写入。系统管理页面提供计划修改、worker 心跳、任务和尝试记录；实际 VPS 的 systemd 服务配置在部署阶段提供。

对于已绑定赛果来源的赛事，足球首次查询为开赛后 120 分钟，未完赛每 10 分钟查询；NBA 首次为开赛后 159 分钟，未完赛每 3 分钟查询。Polymarket 来源赛事须先完成赛果来源绑定才能启用关注与下单；绑定与比分查询已实现，但需要真实密钥在目标环境验证。来源确认完赛后停止常规查询；来源失败和限流保留任务记录。

足球赛事中心顶部显示待确认、自动匹配中、已绑定三类数量；可绑定的未绑定赛事以球队链接显示。只有一个候选时点击球队链接直接绑定；多个候选时展开候选列表后由管理员选择，不会自动选择第一条。自动匹配中的赛事只显示数量，不生成不可操作链接。汇总来自 `GET /result-bindings/summary`，只读取本地已保存候选，不额外请求 API-FOOTBALL。

足球赛果候选会使用内置球队目录中的精确别名以及数据库中已验证的 `TeamAlias` 扩展球队名称。例如 `North Macedonia` 可以匹配 API-FOOTBALL 返回的 `FYR Macedonia`。匹配仍严格要求主客顺序一致且开赛时间差不超过 2 小时，不做模糊匹配，也不会自动确认足球候选；未验证别名不参与匹配。

## Polymarket 市场与钱包

在赛事中心打开详情，选择“搜索候选市场”，然后使用“检查搜索状态”查看结果。系统查询 Polymarket Gamma 的体育事件，按运动、球队、主客顺序和相近开赛时间形成候选；即使名称相似也不会自动确认。请逐项核对来源球队、开赛时间和市场问题，确认或拒绝映射。来源错误、赛事改期或数据超过 15 分钟会使映射不可用于交易；需重新搜索核对。已确认映射可进入单场订单页面；下单时服务端仍会重新核验来源、钱包和盘口。

市场 ID、condition ID、资产 ID 分别保存；对于来源标识为 v1 的市场使用 `clobTokenIds`，v2 使用 `positionIds`。协议版本、组合能力或资产未确认时保持未知。资产变化会使刷新失败并保留旧记录供核查。自动测试只使用明确标记的模拟上游；实际下单仅在管理员确认后执行。

`POLYSPORTS_WALLETS` 是 `.env` 中的 JSON 数组，只接收 `label`、`wallet_address`、`signer_address`、`wallet_type` 和可选的 `credential_ref`，禁止包含私钥；未配置时为 `[]`。可使用如下**模拟配置格式**，部署时必须替换为自己核实的钱包地址：

```dotenv
POLYSPORTS_WALLETS=[{"label":"示例","wallet_address":"0x1111111111111111111111111111111111111111","signer_address":"0x2222222222222222222222222222222222222222","wallet_type":"POLY_PROXY","credential_ref":"primary"}]
```

钱包页面只读展示配置；配置有效凭据时可只读查询 pUSD 余额，未能确认的信息保持未知。每次下单会按选定资产和交易所核验余额与授权，不会自动设置授权或部署钱包。地区受限或无法核验时拒绝下单。

官方参考：[Gamma 事件游标分页](https://docs.polymarket.com/api-reference/events/list-events-keyset-pagination)、[市场字段](https://docs.polymarket.com/api-reference/markets/list-markets)、[Protocol V2 迁移](https://docs.polymarket.com/migrate/polymarket-v2/api-integrations)。

## 交易限额

在「系统管理 → 交易限额」设置单笔可用余额比例、单笔上限最低值和每钱包每日上限。设为 **6%** 和 **1 pUSD** 时，单笔上限为 `min(可用余额, max(可用余额 × 6%, 1 pUSD))`。留空的比例或每日上限不启用对应校验。保存后下一次下单使用新设置，服务器环境配置可提供首次默认值。

单场按限价乘份额、组合按提交预算预占。两类买入共用每钱包的日额度，按 UTC+8 午夜重置。已明确拒绝的提交释放预占，结果未知继续计入当天额度。每日额度统计从此版本启用时开始。

## 钱包诊断与充值

钱包状态页可通过 Polymarket Bridge 查询所选钱包的 Polygon 充值地址、支持资产、合约及最低金额。页面显示返回地址和入账钱包，只提供地址复制。下单页的「检查钱包余额与授权」会重新建立诊断会话，逐步显示地区、凭据、会话和余额授权读取状态。实际市场授权按下单资产与合约检查。

## 只读 Agent

从 `polysports/` 运行 `uv run --locked --extra agent python -m backend.agent_tools`，以 stdio 接入 MCP 客户端。工具提供公开盘口查询和公开持仓估值。设置 `POLYSPORTS_AGENT_WALLETS`（逗号分隔的钱包地址）可允许查询指定钱包的公开组合资产。Agent 进程只需要公开钱包地址，交易提交继续使用网页界面。

## 单场订单与凭据

真实资金单场交易需要使用独立的受限 `.env` 或环境变量配置 `POLYSPORTS_WALLET_CREDENTIALS` JSON 对象，其键对应钱包的 `credential_ref`。每项包含 `private_key`；CLOB 的 `clob_api_key`、`clob_api_secret`、`clob_api_passphrase` 必须全部提供或全部省略，省略时由官方 SDK 获取。智能钱包还须配置 `POLYSPORTS_POLYGON_RPC_URL`，且钱包必须已部署在 Polygon 主网。智能钱包执行赎回时还必须提供完整 Builder 凭证，或 `relayer_api_key` + `relayer_api_key_address`；Relayer API Key 可在 Polymarket 账户 Settings → API Keys 创建，address 使用该 key 对应地址。**不要把真实私钥、凭证或带密钥的 RPC 地址提交到 Git，也不要在浏览器页面输入私钥。**

格式示意（尖括号为占位符，不是可用凭据）：

```dotenv
POLYSPORTS_WALLET_CREDENTIALS={"primary":{"private_key":"<仅在本机安全配置>","clob_api_key":"<可选>","clob_api_secret":"<可选>","clob_api_passphrase":"<可选>","relayer_api_key":"<智能钱包赎回可选>","relayer_api_key_address":"0x..."}}
POLYSPORTS_POLYGON_RPC_URL=<仅在本机安全配置>
```

在赛事详情确认映射后选择某个结果进入单场订单页面，输入方向、限价和份额。与组合交易一致采用**一步式下单**：点一次「按当前价直接下单」即在同一个幂等请求内由服务端重新核对实时盘口、地区、钱包类型、余额与授权，然后签名并提交**真实资金订单**，没有 30 秒预览令牌和二次确认倒计时。页面列出钱包、赛事、选项、限价、份额和预计限价金额供下单前核对；盘口变化后服务端会拒绝提交，需重新填写。订单被接受并不代表成交，订单状态和逐笔成交以交易所返回的证据为准。旧的「预览 → 提交」两步接口仍可用，但不是页面的默认流程。

订单提交或撤单发生超时时，不要重复提交；在交易记录中按原幂等键查询并安排只读对账。若交易所订单编号未知，可只读查询相似的未完成订单；相似并不证明其属于本次提交，只有独立核实后才能手动关联编号。未找到候选不代表订单不存在。后台对账需要运行独立 worker。

本阶段自动化测试使用模拟交易所和测试专用私钥，绝不发送真实订单。真实钱包、额度、签名和部署环境仍需在用户自己的目标环境中单独核验。

## 组合交易

组合交易默认关闭。个人账户使用官方 Requester Gateway 和 CLOB 凭证，不需要 Builder 凭证。钱包必须为已部署的 Deposit Wallet，并配置 Polygon 主网 RPC；在服务器上完成相应余额和 Exchange V3 授权后，通过受限环境变量设置 `POLYSPORTS_COMBO_EXECUTION_ENABLED=true`。不要提交任何真实凭证。FastAPI 必须单进程运行；启用组合功能时应用使用数据库会话锁拒绝第二个 API 进程。后台对账仍由独立 worker 执行。历史 Builder 请求继续使用原网关对账。

在赛事中心确认映射并将不同市场的结果加入组合；系统从官方 Combo 市场目录核对每条腿，至少两腿。填好投注金额后点一次「按当前市价直接下单」即可：官方 Combo 只能经 RFQ 网关成交，网关实时报价即当前组合市场价，服务端在同一个幂等请求内取价并立即签名接受，不再要求先请求报价、再在倒计时内二次确认。系统按报价重新核验有效期、预算上限、余额、授权与凭证；开仓要求赛事映射在 15 分钟内确认，组合平仓不要求；不会自动部署钱包、授权或重发接受请求。报价对象仅驻留 API 进程内存，不写入数据库或浏览器；一步流程在同一进程内立即使用，不会因等待人工确认或重启而失效。发送前校验失败会返回具体原因并把记录标为未成交，可修正后重试。执行中不代表成交，只有上游返回确认或成交状态才标为已确认。下单结果未知时不要另换请求键重试；系统保留未知状态并对已知 RFQ ID 只读对账。上游明确拒绝时，`error_code` 保存上游最具体的失败原因（如 `maker_declined`、`acceptance_window_expired`、`contradictory_legs`），页面显示对应中文说明；接受阶段预写的 `pending` 成交明细会同步作废，结果未知则保留给后台对账。

组合功能的自动化测试使用模拟上游，不发送真实订单；个人账户及真实资金端到端交易尚未验证。官方文档：[Combo Requesters](https://docs.polymarket.com/trading/combos/requesters)。

## 立即平仓

交易记录中已成交的买入单点击「立即平仓」进入独立页面。**单场平仓不需要填写方向、限价、金额或份额**：服务端读取真实盘口买盘并逐档累计深度，得出能一次卖出全部可平仓份额的市价（FOK 限价）与保守预计收入。页面只显示钱包、持仓份额、当前市价和预计收入，点「按当前市价直接平仓」即按该市价提交 FOK 卖单，全部成交或不成交；买盘深度不足或份额低于最小下单量时禁用平仓并说明原因。与开仓一样取消 30 秒市价令牌，盘口变化请先点「刷新市价」；提交时再次核验盘口、余额、授权、原订单身份与幂等键。平仓不依赖赛事映射的 15 分钟确认时效，持仓身份由真实盘口、链上余额与原始订单共同核实。

**已结算或赛果已确认后不再允许平仓**：`backend/close_policy.py` 统一判定 `score_verified`（比赛结束 + 赛果绑定 + 比分非空）或 `accepting_orders is False`（市场停单/结算）；列表接口返回 `close_blocked` / `close_block_reason` 供界面禁用按钮，平仓上下文、FOK 单场预览与提交、带 `parent_combo_id` 的组合报价与接受还会再做一次硬校验并返回 `409 POSITION_SETTLED`。组合按「任一腿确认或停单」判定。

组合平仓同样走官方 Combo RFQ：沿用原组合各腿取得 SELL 报价，要求报价覆盖全部指定份额，并在提交前核验持仓余额与授权。组合没有可直接吃盘的单一市价，但流程已并入一次「按当前市价直接平仓」，不再分「请求真实卖出报价 → 确认接受」两步。**组合平仓与单场平仓一样，不要求赛事映射已确认或仍在 15 分钟时效内**；取价与接受都只核验组合腿的市场与资产身份、原组合成交份额、官方 Combo 目录的持仓编号（position id）及卖出报价资产，开仓仍须先确认映射。确认操作涉及真实资金；执行中不代表成交。未知结果不得重新提交，后台以原请求进行只读对账。

同一钱包的相同资产份额可由多笔订单共享；页面的候选份额根据当前余额、原单已成交数量和本系统已确认的平仓记录计算，不能证明每笔历史订单拥有独立份额。新组合保存官方持仓编号；历史组合需要从原交易成功回执核验该编号和转入数量，无法核实则不能平仓。真实资金链路仍需在目标服务器验证。

## 仓位赎回

交易记录页会对 Polymarket Data API 标记为 `REDEEMABLE` 且当前钱包仍有份额的已结算赢家仓位显示粉色卡片和「赎回」按钮。资格按单场 `token_id` 或组合 `combo_position_id` 匹配，不使用本地赛果或“已结算”推断代替官方持仓状态。

赎回是整仓操作：单场按 `condition_id` 领取该钱包在该市场下的全部可赎回结果份额，组合按官方 `position_id` 领取该组合仓位；不能按单笔订单份额部分赎回。多张订单共享同一市场/组合时，任意一张卡片触发后，其他关联卡片同步显示已赎回。

系统通过官方 `polymarket-client` 的 `redeem_positions` 执行，成功后资金直接回到 Polymarket 现金余额（pUSD），不经过外部钱包。执行前只读检查 Router/Adapter 的 ERC-1155 operator 授权，但不会自动授权、自动部署钱包或自动重发结果未知的请求。智能钱包需要完整 Builder 凭据或 Relayer API Key；EOA 直接签名并支付 Polygon gas。未配置 Polygon RPC、Relayer/Builder 凭据或授权不足时会在发送前拒绝并说明原因。

赎回默认关闭。完成授权和目标环境验证后，在受限配置中设置：

```text
POLYSPORTS_REDEEM_EXECUTION_ENABLED=true
```

`redeem_requests` 以 `(wallet_id,target_type,target_ref)` 保证整仓幂等。成功返回交易哈希、可可靠计算的实际余额增量和当前现金余额；请求一旦可能广播，任何不确定异常都会落为 `unknown` 并禁止重复操作，必须到 Polymarket 或链上独立核对。

## 赛果与结算金额

比赛结束且外部赛果来源已绑定后，可在交易记录的单场订单上点击「核对赛果和市场结算」。页面并列给出**两个相互独立的结算结果**：由已确认比分按市场命题规则推算的胜负与金额（赛果判断），以及 Polymarket data-api 终态二元赔付给出的胜负与金额（市场结算，官方 data-api `payouts` 单位为 micro-USDC/份：`[1000000,0]` / `[0,1000000]` 表示每份 1 / 0 pUSD，同时兼容旧式 `[1,0]` / `[0,1]`；只有终态 `status` 加可用的二元赔付才确认）。理论上两者应一致，因此只有一致时才确认结算金额；不一致时并列保留两个金额、不确认并要求人工核实。市场尚未终态或结算上游暂不可用时，页面给出具体结算阶段（如 `proposed` 已提议结果、处于无争议期）与原因，仍显示按赛果推算的金额，但明确标注为**预计值、未确认**。

**赛事终态与市场终态是两个独立状态**：页面单独显示比赛是否已结束、外部赛果是否已绑定核实，以及 Polymarket 对该 condition_id 的结算状态与结算时间。同一场比赛的胜负、让分、总分等盘口是独立条件，各自结算；赛事结束不等于每个盘口都已进入链上终态。

交易记录页为便于阅读采用三层显示：卡片摘要只留结论（标题带胜负、盘口题目去掉重复队名、价格与份额合并、订单编号缩略）；核对后只出现一行「两个结果一致 / 冲突 / 预计值」结论条；赛事终态、判断依据算式、结算阶段与时间、成交覆盖与免责口径收进「详情」折叠面板，全站口径只在板块顶部写一次。「详情」默认收起但内容完整保留，排查时逐项可查。

**「单场订单」与「组合交易」在桌面左右两列并排，窄屏自动回退为上下单列**。两列都带 `hide_settled=true`：单场隐藏「比赛开赛超过 24 小时且已结算」的记录，组合隐藏「最晚开赛的那场已超过 24 小时且已结算」的记录；已结算判据与 `close_blocked` 一致（外部赛果已绑定核实，或该腿市场已停止接单）。过滤在 `backend/close_policy.py` 统一定义阈值与 SQL 表达式，由 `backend/trading_api.py` / `backend/combo_api.py` 在分页前应用，前端不做二次过滤；不带参数的接口、单条详情、历史与导出仍返回全部记录。

**每张卡片标题右侧直接标注盈亏金额**（`backend/pnl.py`，由列表接口的只读 `pnl` 字段返回，不查询上游）：亏损黑底白字、盈利红底白字、持平灰底白字；盈亏未确认显示中性的「盈亏待确认」，SELL 平仓显示「平仓不适用」。单场 BUY 按二元终态收入减持仓成本，成本优先取完整覆盖 `matched_size` 的 `CONFIRMED` 成交明细，缺失时按「限价 × 份额」估算并在文案前标「约」；组合 BUY 优先用 `combo_fills` 的 CONFIRMED 成交明细（签名接受订单的 `makerAmount` / `takerAmount`；历史组合由官方签名报价按 micro-USDC 精度重建）给出不带「约」的确定金额，明细缺失时才按报价估算并标「约」。悬停徽标可见成本、收入、明细来源与口径说明。徽标是卡片速览，**与下段「两个结算结果一致才确认的应结算金额」是两套口径**：一个允许在成交明细缺失时明确标注估算，一个只用已确认数据；二者都不能代表链上赎回或实际到账。

**组合买入卡片在标题下用三张小卡片直接给出份额总额、买入价格与买入金额**（列表接口只读 `buy_summary`，由 `backend/combo_fills.py::buy_summary()` 计算）：有 `combo_fills` 的 CONFIRMED 明细时份额取 `takerAmount`、金额取 `makerAmount`、每份价格为金额除以份额，均为确定值；明细缺失时按官方签名报价给出份额与 `blended_price`，金额按 `blended_price × takerAmount` 以 micro-USDC 精度重建并标「约」；校验不通过则金额写「待核实」。`quantity` 是 BUY 预算、`total_required` 只是接受报价所需余额，两者都不会被当份额或实际支出，也不再把 `quantity` 错标成「份」。每条腿的摘要、「详情」与「逐腿与报价明细」都拆成分层小卡片：逐腿核对每腿一张、组合结论一张、口径说明一张，卡内标签左对齐、值右排，窄屏自动单列。

赛果判断按系统实际支持的三类全场市场推算，并显示具体计算依据：胜负（队伍选项或 `Will X win on...?` Yes/No）；大小分/总进球（`总分 = 主队比分 + 客队比分`，与 `O/U`、`Over/Under`、`Total` 等题目中的盘口比较）；让分/让球（仅当选项自身写明球队与让分数，如 `Cavaliers -4.5`，按分差加让分数判断）。例如比分 `127:117`、盘口 `227.5` 时，`Under` 明确未获胜。半场、局节、单队、球员市场，足球加时/点球等非 `FT` 状态，盘口缺失或题目与选项数字冲突，以及总分或让分正好等于盘口的走盘情形，一律不从比分推断，并说明具体原因。

对已成交的买入单，两个结果各自按终态二元赔付计算：所选选项获胜为 `成交份额 × 1 pUSD`，未获胜为 `0`。成交成本与已实现盈亏只在结算金额已确认、且本系统已保存的 CONFIRMED 成交明细份额之和严格等于订单已成交份额时才显示；明细不足时先点击「查询成交记录」补齐证据，页面会说明原因，不用限价猜测成交价。卖出平仓单按成交价结算，不适用市场最终赔付。这些金额是按市场规则计算的**应结算金额**，不含未记录的费用，也不代表链上赎回或资金实际到账；组合交易没有单一终态赔付口径，不在此处计算金额（组合胜负核对见下一段）。

组合交易记录列表（`GET /combo-rfqs`）直接给出每腿赛果判断与组合层按赛果判断结论，纯本地只读、不查询上游；另有「核对组合赛果和市场结算」只读入口（`GET /combo-rfqs/{rfq_id}/resolution`）逐腿复用单场的赛果判断规则与 Polymarket `/v2/resolutions`，并列显示每腿的赛事终态、赛果判断依据、该腿底层市场的结算阶段与单腿核对结论。组合层按串关全中口径汇总：全部腿命中才算组合获胜，任一腿明确未命中即组合未获胜，任一腿无法判断或尚未终态则整单不确认；两个结果一致才确认组合胜负，冲突时要求人工核实，仅有赛果判断时标注为预计值。组合仓位没有单一二元 condition，结果二由各腿底层市场的终态结算汇总，实际赔付以官方组合仓位终态为准；该只读核对接口**不计算组合结算金额**，页面明确标注「不计算结算金额」。SELL 组合平仓按卖出报价成交，标注不适用终态胜负核对。市场终态查询逐腿串行，单次最多 20 条腿。

组合成交明细由 `combo_fills` 表（Alembic 迁移 `b5d2e7c41a90`）保存：接受报价时在同一事务写入签名订单实际支出 `makerAmount` 与实际份额 `takerAmount`（`state:pending`），RFQ 进入 `CONFIRMED` 才确认并回填 `tx_hash`，终态失败/过期/拒绝则作废，不会把未成交报价当成确定盈亏。迁移对历史已确认 BUY 组合按 `blended_price × takerAmount` 以 micro-USDC 精度重建实际支出，并用 `total_required >= 重建成本` 校验；字段不完整或校验不通过的记录不回填，卡片继续显示带「约」的估算。因此组合卡片徽标在有明细时是不带「约」的确定盈亏，与此处「不计算结算金额」是两套口径，不可当作链上结算金额使用。

## 历史、统计和导出

“历史与导出”按运动、UTC+8 日期、赛事状态、钱包、交易类型及交易状态筛选；结束日期不含当天。赛事按开赛时间筛选，交易按创建时间筛选。导出采用最近一次应用的筛选条件，覆盖所有匹配记录而不是当前页面；CSV 和 Excel 的时间列标注 UTC+8，文本字段防电子表格公式注入。Excel 将标识作为文本保存，避免大整数精度丢失。

统计的单场成交只包括本地已保存、上游状态为 CONFIRMED 的成交记录；组合确认数单独列出，不等于单场成交数。结算金额在交易记录页按赛果判断与市场终态两个结果交叉核对后逐笔确认，本系统未持久化结算结果，因此统计中的已实现收益仍显示未知，导出文件中的收益空白表示未知。钱包、交易类型和交易状态筛选只影响交易统计，不影响赛事总数。系统管理页提供数据源非秘密配置状态、同步日志、worker 心跳、任务与审计记录。

## 每日盈亏日历

“每日盈亏日历”（`/pnl-calendar`，`GET /api/v1/pnl-calendar?month=YYYY-MM`）按月网格展示每天的单场与组合投注盈亏，用颜色区分盈亏（红底盈利、黑底亏损、灰底持平、浅黄底盈亏待核实、中性底待结算），点击日期展开足球 / 篮球明细。归日**按下单时间**：北京时间 12:00 至次日 11:59 记为同一天，因此部分比赛会在次日凌晨结算后才计入前一天。投入合计当日全部下单成本（含未结算）。

每笔投注分三档互斥状态，不混用：**已结算**（盈亏可严格核实，计入返奖与盈亏合计）、**盈亏待核实**（比赛已结束且赛果已确认，但该盘口口径无法按比分严格推断，如让分/大小分规则不明，计入投入与笔数但不计入盈亏合计，绝不猜测金额）、**待结算**（赛果尚未核实）。因此同一天可以同时出现“已结算 N 笔 · 盈亏待核实 M 笔”，盈亏合计只反映能核实的那部分，不会因为一笔无法核价就整日标成待结算。

盈亏口径与交易记录卡片完全同源（`backend/pnl.py` 的 `single_pnl` / `combo_pnl`），不查询 Polymarket 实时终态，也不使用未持久化的结算时间戳：赛果已核实 + 比赛结束 + 比分按市场命题规则推断，成交明细完整覆盖时成本为确定值，否则按限价估算并以 `has_estimate` 标出。盈亏待核实的投入单独计入 `unpriced_invested`，与 `settled_invested` 分开，避免盈亏被算成全额亏损。组合按腿所属运动归入足球或篮球，跨运动组合单列“跨运动组合”，不重复计入两个运动。金额单位为 pUSD，为按市场规则推算的应结算金额，不含未记录费用，不等于链上赎回或实际到账。

```bash
uv run --locked pytest -q
```

```powershell
$env:POLYSPORTS_TEST_DATABASE_URL = 'postgresql+psycopg://测试用户:测试密码@127.0.0.1:端口/polysports_test_临时库'

```

自动测试不证明外部赛事 API、真实钱包权限或真实资金交易可用；部署与恢复说明见 [DEPLOY.md](../DEPLOY.md)。
